🚨 La Realidad del Desarrollo: Tu App Funciona, pero Está Críticamente Vulnerable

En la práctica anterior lograste desplegar con éxito tu backend en Render conectado a MongoDB Atlas. ¡Enhorabuena! Sin embargo, cometiste (a propósito de este laboratorio) el pecado capital número uno del desarrollo web: dejaste tu contraseña de base de datos escrita en texto plano dentro de awcodeAtlas.js. En esta práctica aprenderás a erradicar este fallo de raíz, entenderás por qué un PaaS como Render no permite subir archivos .env por SSH, y demostrarás en los logs que tu aplicación se alimenta de variables de entorno seguras.

Sección 1

El Gran Peligro: ¿Por qué es un desastre dejar contraseñas en el código?

Cuando ejecutas git push con una línea como mongodb+srv://usuario:Pepito123@cluster0..., se desata una cadena de amenazas inmediatas:

🤖 1. Rastreadores en Tiempo Real
Existen miles de bots automatizados escaneando las APIs de GitHub las 24 horas. En menos de 5 segundos tras tu push, extraen tu usuario y contraseña.
💸 2. Facturas de Miles de Euros
Un atacante puede utilizar tu clúster o los servicios asociados para inyectar terabytes de tráfico, aprovisionar recursos o minar criptomonedas (Cryptojacking).
⚖️ 3. Sanciones Legales (RGPD)
Si te roban datos de usuarios (nombres, correos, tareas privadas), la legislación europea (RGPD / LOPD) impone multas de hasta el 4% de la facturación global o millones de euros.
🎭 4. Sabotaje, Defacement y Rescate
Pueden borrar tus listas y pedirte Bitcoin (Ransomware), o inyectar "cosas feas" (insultos, pornografía o mensajes ofensivos) en tu To-Do List visible en Internet.
⚠️ LA COMBINACIÓN EXPLOSIVA: En la práctica anterior configuramos en MongoDB Atlas la regla 0.0.0.0/0 (acceso desde cualquier IP del planeta). Al no haber cortafuegos de red restringido, la contraseña era la ÚNICA barrera de seguridad. Al dejarla en GitHub, le abriste la puerta de par en par a cualquiera.
Sección 2

¿Por qué Render no tiene un archivo .env? Entendiendo IaaS, PaaS y SaaS

Muchos alumnos preguntan: «Profe, si en local uso un archivo .env, ¿por qué no puedo simplemente conectarme por FTP/SSH a Render y subir mi archivo .env allí?» La respuesta se encuentra en el modelo de servicio cloud:

Modelo Cloud Ejemplos Reales ¿Qué gestionas tú? ¿Cómo se configuran los secretos?
🖥️ IaaS
Infrastructure as a Service		 AWS EC2, Google Compute Engine, Azure VMs La máquina virtual completa, parches del SO, Nginx, Node.js y los discos persistentes. Tienes acceso SSH: Puedes conectarte con terminal y crear físicamente el archivo .env en el disco de la máquina.
🚀 PaaS (Render)
Platform as a Service		 Render, Heroku, Google Cloud Run, Fly.io SOLO TU CÓDIGO. La plataforma gestiona servidores, parches, escalado, contenedores y certificados SSL. NO hay SSH ni disco persistente. Los contenedores son efímeros. Los secretos se inyectan como Variables de Entorno desde el panel web de la plataforma.
📱 SaaS
Software as a Service		 Gmail, Trello, Jira, Google Drive, Canva NADA técnico. Solo consumes la aplicación como usuario final a través de la web o app móvil. ¡No se hace! El usuario final no toca base de datos ni variables de entorno; el proveedor se encarga de todo internamente.
💡 Conclusión clave: Igual que Render ya te inyecta automáticamente la variable de entorno PORT para que tu servidor Express sepa en qué puerto escuchar (process.env.PORT), nosotros podemos crear en su panel web nuestra propia variable atlas_url con la cadena de conexión de MongoDB.
Paso a Paso

Guía Práctica: De Localhost a Render sin Exponer Contraseñas

Paso 1: Instalar la librería dotenv en tu proyecto

Abre tu terminal en la carpeta del repositorio y ejecuta:

npm install dotenv

Paso 2: Crear la carpeta credentials/ y tu archivo secreto .env

  1. Crea una carpeta llamada credentials en la raíz del proyecto.
  2. Dentro de ella, crea un archivo llamado .env (¡con el punto delante!).
  3. Pega tu URL de Atlas asignada a la variable atlas_url:
# Archivo: credentials/.env (¡ESTE ARCHIVO NUNCA SE SUBE A GITHUB!)
atlas_url=mongodb+srv://TU_USUARIO:TU_PASSWORD@cluster0.n87gd.mongodb.net/todolistDB?retryWrites=true&w=majority
PORT=3000

Paso 3: Proteger el secreto con .gitignore

Abre el archivo .gitignore y comprueba que incluye la carpeta de credenciales: 

# En tu archivo .gitignore:
credentials/.env
credentials/*.env

Prueba del algodón: Ejecuta git status en tu terminal. El archivo credentials/.env NO DEBE APARECER. Si aparece en rojo, revisa tu .gitignore antes de hacer commit.

Paso 4: Actualizar el código en awcodeAtlas.js

Abre [awcodeAtlas.js](file:///Users/fjbanezares/express-mongo-hands-on/awcodeAtlas.js) y sustituye la conexión antigua por este bloque seguro: 

// 1. Cargar variables desde credentials/.env (solo en desarrollo local)
require("dotenv").config({ path: "credentials/.env" });

// 2. Extraer la URL de MongoDB desde las Variables de Entorno del sistema
const MONGODB_ATLAS_URI = process.env.atlas_url || process.env.ATLAS_URL;

// 3. Auditoría de Seguridad mediante Logs (Enmascarando contraseñas)
console.log("============================================================");
console.log("🔒 [AUDITORÍA DE SEGURIDAD]");
if (MONGODB_ATLAS_URI) {
  // Reemplaza la contraseña por asteriscos para no exponerla en pantalla
  const maskedURI = MONGODB_ATLAS_URI.replace(/:([^:@]+)@/, ":****@");
  console.log("✅ Variable de entorno 'atlas_url' detectada y activa.");
  console.log("📡 Conexión segura a Atlas:", maskedURI);
} else {
  console.error("❌ ERROR CRÍTICO: La variable 'atlas_url' no está configurada.");
}
console.log("============================================================");

// 4. Conectar a Mongoose
mongoose.connect(MONGODB_ATLAS_URI, { useNewUrlParser: true, useUnifiedTopology: true });

Paso 5: Probar en Local y Subir a GitHub

  1. Prueba en tu máquina: node awcodeAtlas.js. Verifica que arranca y que el log muestra la URL con ****.
  2. Haz commit y sube a GitHub:
git add .
git commit -m "feat(security): aislar credenciales en variables de entorno"
git push origin main

Abre tu repositorio en la web de GitHub y navega a awcodeAtlas.js: ¡Comprueba con orgullo que ya no hay ninguna contraseña visible!

Paso 6: Configurar la Variable de Entorno en Render

  1. Entra en tu panel de dashboard.render.com.
  2. Haz clic en tu Web Service.
  3. En el menú lateral izquierdo, haz clic en la pestaña Environment.
  4. Pulsa en Add Environment Variable:
    • Key: atlas_url
    • Value: (Pega tu cadena completa de Atlas: mongodb+srv://usuario:password@...)
  5. Pulsa el botón azul Save Changes.

Paso 7: Comprobar el Redespliegue y los Logs de Render

Render detectará la nueva variable y relanzará automáticamente tu aplicación. Ve a la pestaña Logs de Render y verás: 

==> Starting service with 'node awcodeAtlas.js'
============================================================
🔒 [AUDITORÍA DE SEGURIDAD]
✅ Variable de entorno 'atlas_url' detectada y activa.
📡 Conexión segura a Atlas: mongodb+srv://tu_usuario:****@cluster0...
============================================================
Server started on port 10000
Database connected successfully!

📹 Entregable 2: Vídeo de Reflexión Técnica (Máximo 2 minutos)

Graba un vídeo breve explicando cómo te has sentido al implementar esta arquitectura de seguridad y responde con tus propias palabras a las siguientes 7 preguntas clave (apóyate en las pistas proporcionadas):

1. ¿Por qué es crucial entender la diferencia entre IaaS y PaaS al gestionar secretos?
💡 Pista: Compara una máquina virtual clásica (IaaS con disco fijo y acceso SSH por terminal) frente a los contenedores efímeros de Render (PaaS), que se destruyen y recrean descargando el código de GitHub (¡donde el archivo .env jamás debe estar!).
2. ¿Cómo se configuraría este archivo de contraseñas en un modelo SaaS (Software as a Service)?
💡 Pista: ¡Cuidado, es una pregunta trampa! En un SaaS como Gmail, Trello o Canva, el usuario final NO gestiona código ni servidores ni bases de datos. Solo consume el software. Toda la seguridad de infraestructura es 100% invisible y responsabilidad exclusiva del proveedor SaaS.
3. La falacia de "lo borro en el siguiente commit": ¿Por qué sigues en peligro si borras la contraseña en un commit posterior?
💡 Pista: Recuerda la inmutabilidad de Git. Cada commit es una foto eterna. Cualquier persona o bot puede ejecutar git log -p o inspeccionar el historial de commits en GitHub y ver el archivo tal como estaba antes de borrar la contraseña.
4. La regla 0.0.0.0/0 frente a la contraseña: ¿Qué ocurre con la "Defensa en Profundidad"?
💡 Pista: Al abrir el cortafuegos de Atlas a cualquier IP pública para que Render pudiera conectar, eliminamos la barrera de red perimetral. La contraseña era la ÚNICA cerradura de la casa. Si dejas la llave puesta en la puerta abierta, no te queda ninguna capa de defensa.
5. ¿Por qué hacer un console.log(process.env.atlas_url) sin enmascarar es una vulnerabilidad grave?
💡 Pista: En entornos reales los logs no se quedan en tu consola: se envían a plataformas centralizadas (Datadog, CloudWatch, Papertrail) donde decenas de personas tienen acceso de lectura. Si imprimes la contraseña en texto plano, vuelves a filtrarla a terceros.
6. El principio de los 12 Factores: ¿Por qué separar Configuración de Código permite portabilidad total?
💡 Pista: Si tu código solo busca process.env.atlas_url, el mismo archivo exacto funciona en tu portátil (apuntando a tu BD de pruebas), en staging (pre-producción) y en Render (producción) sin tener que tocar ni una sola línea de código JavaScript.
7. Responsabilidad legal y económica: Si un bot roba tus claves, ¿de quién es la culpa ante la ley?
💡 Pista: Ni MongoDB Atlas ni GitHub se hacen cargo de tus descuidos. La custodia de credenciales recae 100% sobre el titular de la cuenta. Las multas del RGPD y las facturas por abuso de recursos las paga el desarrollador o la empresa titular.
